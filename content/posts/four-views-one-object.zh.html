本文讲的是我在一家创业公司做机器学习工程师时的工作。模型名称、提示词和产品内部细节都略去了，数字来自我们当时自己的评测。

需求听起来很简单。用户上传一张物体的图，可能是一把椅子、一只怪兽或一个角色，要求生成四个标准视图，好让重建管线据此建出网格。任何一个能力不错的图像模型，都能生成四张好看的图。问题在于，「好看」不是需求。需求是四张图画的必须是同一个物体：比例相同，颜色相同，装饰相同；左视图要是右视图的镜像；背视图要保持正视图确立的身份特征。四次独立生成几乎永远做不到这一点，你得到的是四个长得像的表兄弟。

为什么评审要单独一个 Agent

系统是一个 ReAct 循环，串起八个专用 Agent：需求理解、逐视图的提示词优化、生成、单图评估、跨视图评估、定向编辑、外部检索，以及一个决定下一步做什么的控制器。其中最关键的拆分，是把生成者和评审者分开。

让模型先生成、再给自己的作品打分，它会对自己很宽容。生成者的任务是尽力去做；评审者的任务是找问题，而它在从没见过生成提示词、只看得到原始需求和四张全分辨率结果并排摆在一起时，找得最好。它先给每张视图打分：是否符合提示词、画面质量、朝向是否正确、主体是否完整没被裁掉。再给整组打分：几何与身份是否一致，颜色与装饰是否一致，比例是否对齐，用户要求的每一处修改是否在每张视图里都体现了。输出是结构化的：总分、每张视图的问题及严重程度、需要重新生成的视图列表，以及修改建议。

循环出过几次错之后，我加了一条规则：评审的输出如果解析不了，算失败，而不是算通过。第一版在解析出错时默认「没问题」，悄悄放过了好几组不合格的结果。

只重做一个视图，而不是四个

最朴素的重试策略是：评审不满意，就整组重新生成。这样不仅贵，更糟的是会扔掉已经正确的视图，换上未必正确的新图。所以这个循环只做局部修复：

  • 一张侧视图不合格：只重新生成那一张，以正视图和合格的另一侧作为参考。
  • 几张视图不合格：只重新生成被标记的那几张。
  • 正视图不合格：整组重建。正视图是其他视图继承身份特征的参考，坏掉的正视图无法绕过去修补，它会一路传染下去。

这跟卡牌数值稍微超一点就往回调、而不是直接扔掉，是一个道理：哪里错了只修哪里。依赖结构让这件事行得通。先生成正视图，它成为锚点。左右视图对照正视图生成，并明确要求两者画的是相对的两侧；如果是角色或动物，四肢姿态也要互为镜像。背视图继承正视图。当评审标记左视图有问题时，控制器清楚地知道该把哪些参考图交给生成者去重做。

什么时候该停

一个随时可以再试一次的循环，就会一直再试下去。所以同时设了三道上限，先碰到哪道就在哪停：质量阈值、最大迭代轮数（四轮），以及用户的订阅额度。额度在开始时预留、结束时结算，失控的循环也不会超支。碰到上限不等于失败。每一组候选都带着分数存成版本，控制器返回见过的最好版本；如果后面某一轮反而变差，也能回退过去。

质量阈值是动态的，这是最微妙的部分。只有两个约束的请求（「一把红色的椅子」）和有九个约束的请求（「一把红色天鹅绒扶手椅，铜钉装饰，左边坐垫破了，上面睡着一只猫」），不应该用同一条「完全满足所有条件」的标准来衡量。需求理解 Agent 提取出的约束越多，阈值就在一定范围内放得越宽。没有这一点，复杂请求会一路跑满四轮，最后照样返回一个差一点点的结果；有了它，它们会更早停在那个差一点点的结果上，省下最后两轮的花费。

结果。超过 90% 的请求在两轮迭代内收敛到评审认可的输出。剩下的大多是真正难的主体跑满了轮数上限，比如严重不对称的物体，「左右镜像」根本没有干净的答案，最后交付的是最好的那一版。

这个循环的代价

拆成多个 Agent 是有代价的：更多 token，更高延迟，步骤之间要传递更多状态，出了问题也更难说清该怪哪个 Agent。这个代价值得付，有两个原因。局部重生成让一次重试的成本降到整组的大约四分之一。而每一步的想法、动作、观察和版本都留有可重放的记录，失败变得可以调试：用户反馈结果不好时，我可以重放那次运行，找到放过它的那一次评审调用。

这个项目我最大的收获不是哪个 Agent，而是这个循环的样子，后来在一个完全不同的问题上又用上了：先生成；让不是生成者的人来判；哪里错了只修哪里；每一版都存下来；停下来时要说得出为什么。负责生成的那个，反倒是最不重要的一环。

同样的循环形状，把评审换成确定性校验器，见《这卡超模了吗》；把评审换成真机，见《知道那个按钮叫什么》。
