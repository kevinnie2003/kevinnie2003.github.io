本文讲的是我在一家创业公司做机器学习工程师时的工作。模型名称、提示词和产品内部细节都略去了，数字来自我当时自己做的评测。

需求听起来很简单。用户上传一张物体的图，可能是一把椅子、一只怪兽或一个角色，系统要生成四个标准视图，让重建管线据此建出网格。随便一个不错的图像模型，都能画出四张好看的图，可需求不是好看，而是四张图画的必须是同一个物体：比例、颜色、装饰都一样；左视图和右视图要互为镜像；背视图要保留正视图里的外观特征。四张图分开生成，几乎不可能做到这一点，结果往往是四个长得差不多、细节却对不上的东西。

为什么评审要单独一个 Agent

系统是一个 ReAct 循环，串起了八个专用 Agent：需求理解、给每个视图优化提示词、生成、单图评估、跨视图评估、定向编辑、外部检索，还有一个决定下一步做什么的控制器。其中最关键的一点，是把生成和评审分开。

让同一个模型先生成、再给自己打分，它会对自己很宽容。生成的一方只管尽力画好；评审的一方专门找问题。评审最好别看到生成用的提示词，只看原始需求，再把四张全分辨率的结果并排放在一起看，这样问题找得最准。它先给每张图单独打分：符不符合提示词、画面质量、朝向对不对、主体有没有被裁掉。再给整组打分：形状和外观特征是否一致，颜色和装饰是否一致，比例是否对得上，用户要求的每一处修改是不是在每张图里都改到了。输出是结构化的：总分、每张图的问题和严重程度、需要重画的视图，还有修改建议。

循环出过几次错以后，我加了一条规则：评审的输出解析不了，就算不通过。第一版在解析出错时默认「没问题」，悄悄放过了好几组不合格的结果。

只重做出问题的那张

最简单的重试办法是：评审不满意，就整组重画。这样不光贵，还会把已经画对的图扔掉，换上不一定对的新图。所以这个循环只做局部修复：

  • 一张侧视图不合格：只重画那一张，拿正视图和合格的另一侧当参考。
  • 几张视图不合格：只重画被标出来的那几张。
  • 正视图不合格：整组重来。其他视图都照着正视图画，正视图错了，别的图跟着错，没法绕过它单独修。

这和卡牌数值稍微超一点就往回调、不直接扔掉，是一个道理：哪里错了就只修哪里。能这样做，是因为各个视图之间有明确的依赖关系：先生成正视图，把它当作锚点；左右视图照着正视图生成，并且明确要求两张画的是相对的两侧，如果是角色或动物，四肢的姿势也要互为镜像；背视图也照着正视图来。所以评审说左视图有问题时，控制器很清楚该把哪几张参考图交给生成的一方去重画。

什么时候该停

循环只要还能再试，就会一直试下去。所以我设了三道上限，碰到哪一道就停：质量阈值、最多迭代轮数（四轮）和用户的订阅额度。额度在开始时先预留、结束时再结算，就算循环失控也不会超支。碰到上限也不算失败：每一组结果都连同分数存成一个版本，控制器最后返回分数最高的那一版；后面哪一轮反而变差了，也能退回去。

质量阈值是动态的，这是最需要拿捏的地方。只有两个条件的请求（「一把红色的椅子」）和有九个条件的请求（「一把红色天鹅绒扶手椅，铜钉装饰，左边坐垫破了，上面睡着一只猫」），不该用同一条「全部满足」的标准来衡量。需求理解 Agent 提取出的条件越多，阈值就在一定范围内放得越宽。不这样做的话，复杂请求会一路跑满四轮，最后照样只拿到一个差一点点的结果；这样做了，它们会更早停在这个差一点点的结果上，省下最后两轮的钱。

结果。超过 90% 的请求在两轮以内就得到了评审认可的结果。剩下的大多是确实难画的东西，比如严重不对称的物体，根本谈不上「左右镜像」，这些会跑满轮数，最后交出最好的那一版。

这个循环的代价

拆成多个 Agent 是有代价的：token 更多，延迟更高，步骤之间要传的状态更多，出了问题也更难说清该怪哪个 Agent。但我觉得值得，原因有两个。一是只重画出问题的那张，一次重试的成本大约只有整组重画的四分之一。二是每一步的想法、动作、观察结果和版本都有记录，可以重放，出了问题能查：用户反馈结果不好时，我可以把那次运行重放一遍，找到是哪一次评审放过了它。

这个项目给我最大的收获不是某个 Agent，而是这个循环的结构，后来我在一个完全不同的问题上又用上了它：先生成；让生成者以外的一方来评；哪里错了只修哪里；每一版都存下来；停下来时要说得出为什么。生成本身反倒是最不重要的一环。

同样的循环，把评审换成确定性的校验器，可以看《这卡超模了吗》；把评审换成真机，可以看《知道那个按钮叫什么》。
